# Database contract for the Everneed app and website (live Supabase `zpgasfweaixwsktlueje`)

Snapshot taken **12 Nov 2026** from the live database. This contract applies to the app and website because they are parts of the same Everneed platform and use the shared Supabase backend. The function map records known website and app call sites, with app coverage distinguished as static source evidence versus live/device verification. Do not assume a function is app-integrated merely because it exists in the database.
If you change the database, update this file in the same commit. Status words are defined in `AI_PROTOCOL.md`.

A second database, **staging** (`Everneed-staging`, ref `vjiadqygpyebpisxslbx`), is the development and test environment. It is kept production-compatible at the schema, migration, policy and backend-contract level, while using separate test Auth users and test data. It is not a connection to the live production database. Live is the only database described below. How the two relate, and how a change moves between them, is in `ENVIRONMENTS.md`.

## Branch and database workflow
- App and website changes are developed together on `web-portal` and released together to `main` through a reviewed pull request.
- Both clients must use the same documented function signatures, status rules, money rules and RLS expectations. Put reusable client helpers in `shared/`.
- Database changes must be committed as numbered files in `supabase/migrations/` before they are applied anywhere. They reach staging only through a manually dispatched, owner-approved `staging-db.yml` workflow, and live by hand with separate owner approval. Update this contract and the project tracker in the same change.
- Verify the Supabase project reference before applying any migration. Never apply a migration to a different project based only on a copied project ID.

## How the app and website talk to the database
- Browser client: `shared/supa.js` (`Supa.get`, `insert`, `patch`, `rpc`, `rpcAnon`, `fn`, `upload`). Public waitlist and guest-support writes use the `public-forms` Edge Function when the page is running against staging. Public anon key in `shared/config.js`, which also holds the staging key and picks one by page address.
- Row Level Security is **on for every public table**. RLS controls rows, but SQL object grants and function EXECUTE privileges are separate controls; review all three. The browser should never receive privileges beyond its intended role and policies.
- Money movement and protected order/store transitions are implemented through privileged database functions and guards. Do not assume every SECURITY DEFINER routine has the same authorization pattern: the live inventory found 84 application routines, 58 SECURITY DEFINER functions, and six SECURITY DEFINER functions with PUBLIC EXECUTE. Their caller checks, ACLs, search paths, and exposed-schema reachability must be reviewed individually. The app and website should use approved RPCs rather than writing protected tables directly.
- Payments: edge function `paystack` (HMAC-verified webhook, `verify_jwt` off by design). Not yet called by the website; app integration must be verified during the app audit.

## Staging-only seller legal and activation controls (migrations 019–023; 12 Nov 2026)

These are newer development contracts applied to **Everneed-staging only**. They are not yet in the live schema and must not be described as live production behaviour.

- policy_documents: country- and locale-specific policy catalogue. Only published and effective documents are readable publicly; authenticated admins can manage policy publication.
- policy_acceptances: immutable account-to-policy-version acceptance evidence. Browser writes are RPC-only through accept_policy(p_document_id,p_country).
- collections: managed seller category catalogue. Migration 023 seeds the initial marketplace categories; the seller wizard reads this table instead of maintaining a separate browser taxonomy. Admins can manage it centrally.
- seller_verification_rules: enabled/required checks per country. Nigeria currently requires phone, identity, face_liveness and business_address. Other markets have no enabled seller rules until configured and approved.
- store_verification_checks: private per-store verification state. Seller can read their own status; only trusted service/provider workflows can write outcomes. No client-side “verified” flag is accepted.
- seller_verification_reminder_state: seven-day per-store/check reminder cooldown to avoid repeated notifications.
- stores.activation_status: separate from application stores.status and store_applications.decision. New/approved stores remain verification_required until the server activation RPC succeeds.
- request_store_activation(p_store): seller-owned RPC; requires admin-approved application and all enabled required checks to be verified and unexpired. It returns the missing checks or marks activation live.
- private.store_live(p_store): public store/product visibility now also requires activation live, current verification and a valid subscription. Official store remains exempt.
- submit_store(p_store): staging override requires explicit acceptance of the latest effective published English regional seller_terms, seller_privacy, marketplace_rules and returns_refunds documents before application submission. Migration 022 closes the stale-version acceptance gap.
- approve_store: admin approval sets application decision approved but resets activation to verification_required; its notification explicitly says verification is still needed. It does not bypass the activation gate.

Staging application evidence: migrations 019–023 are present in Everneed-staging migration history. A catalog check confirmed four enabled required Nigeria checks, separate anonymous/authenticated policy read policies, no anonymous EXECUTE on is_admin(), no authenticated update privilege on stores.activation_status, no seller INSERT on store_verification_checks, and the approval/live-store function definitions enforce the gate. The Supabase security/performance advisor still reports pre-existing findings (for example kv/rate_limits intentionally have no policies; several older RLS initialization-plan and SECURITY DEFINER warnings remain). Review new findings before promotion.

Not yet implemented: customer signup policy acceptance, published legal documents, identity/face/address provider integrations, SMS OTP, secure document submission/review UI, scheduled reminders, plan selection and app parity. Do not promote these migrations to live until the full review and staging tests pass.

### Seller order RPC — staging audit (23 Nov 2026)

**Verified read-only against Everneed-staging `vjiadqygpyebpisxslbx`.**

- `my_seller_orders(p_status text default null)` returns seller-owned released orders and snapshots: order/seller-order IDs, status, route, subtotal, commission, earnings, accept_by, created_at, customer name/city, conditionally phone/address, and items (`id,name,size,qty`). Direct-delivery private contact fields are withheld until accepted or later; hub orders show first name/city only.
- `seller_transition(p_so text, p_to text, p_payload jsonb default '{}')` is SECURITY DEFINER and enforces authenticated caller, throttling, row lock, store ownership/admin, released-payment check, allowed transition, protected delivery/hub transitions, notification, audit and parent-order sync.
- Allowed seller transitions: pending→accepted/rejected/cancelled; accepted→preparing/cancelled; preparing→ready/cancelled; ready→cancelled, or route-specific direct→out_for_delivery / hub→handover_pending. The wider delivery/admin state machine includes handover_pending→at_hub/cancelled, at_hub→consolidated, consolidated→out_for_delivery, out_for_delivery→delivered and issue→ready/at_hub/cancelled (issue is admin-only). Seller RPC blocks direct updates to delivered, at_hub and consolidated.
- Payload: reject requires `reason` length ≥3; direct-dispatch optional `courier_name` max 80, `courier_phone` max 30, `note` max 300. Transition timestamps are set by backend.
- **Not yet verified/implemented:** explicit accept-deadline (`accept_by`) guard within `seller_transition`; seller order-event timeline; frontend actions. Do not enable Accept until the deadline/race behavior is checked and tested.
- No new migration is needed merely to create accept/reject/prepare/ready/handover actions. The frontend can use `Supa.rpcAuth("seller_transition", {p_so, p_to, p_payload})` after the deadline hardening.

### Public RPC security controls (migration 016; staging verified, production pending owner approval)
- Guest support RPCs validate visitor IDs consistently (20–64 URL-safe characters); the frontend currently generates 24 random bytes with Web Crypto and keeps the identifier out of URLs.
- Guest session creation, heartbeat and close calls are rate-limited by the Supabase-provided `X-Forwarded-For` request header. Waitlist joins are limited by both client IP and normalized email. Limits are transaction-serialized to prevent concurrent-request races.
- Rate-limit identifiers are keyed pseudonyms using a random pepper held in the RLS-protected `kv` table; raw IP/email values are not persisted in `rate_limits`.
- Migration 018 revokes direct `PUBLIC`, `anon` and `authenticated` EXECUTE on `join_waitlist` and all three guest-support write RPCs; only `service_role` can call them. The browser must call `public-forms`; once `TURNSTILE_SECRET_KEY` is configured, it validates Cloudflare Turnstile for waitlist and guest-open requests before invoking the RPCs. Guest ping/close are proxied through the same Edge Function and require the unguessable visitor ID. The two aggregate-only read RPCs remain public.
- Closed guest sessions cannot be reopened using the same identifier. Guest ping/close calls cannot mutate malformed identifiers.
- The two public SECURITY DEFINER aggregate-read warnings (`support_sla_public`, `store_reply_stats`) are intentional. The four write-oriented guest/waitlist RPCs are no longer directly executable by API roles after migration 018.

### Authenticated SECURITY DEFINER audit and hardening (migration 017; staging verified 12 Nov 2026)
- A read-only first-pass audit covered all 38 public SECURITY DEFINER routines executable by `authenticated`, including the six intentional public/anonymous endpoints.
- Migration 017 pins every one of those routines to an empty `search_path`; their referenced tables and helper functions are schema-qualified. No function ACLs were broadened.
- `chat_start` now requires an attached order to contain the selected store as a seller and bounds chat subject/first-message input.
- `hub_receive` now requires exactly one valid check result per order item and rejects duplicate, unknown, extra or missing item IDs.
- `support_sla_sweep` now distinguishes authenticated JWT callers from service-role/cron invocations; authenticated calls require admin status even if the JWT subject is absent.
- Regression tests cover cross-store order/chat binding, duplicate hub checks, malformed authenticated claims, seller denial of an admin payout RPC, empty search paths, and explicit function grants.
- Migration 017 applied successfully to staging in workflow run `43244981357`. Its regression tests passed in run `43245491269`; catalog verification confirmed 38/38 empty search paths and zero PUBLIC EXECUTE. Production remains untouched pending explicit owner approval.

**How the eight missing files were recovered.** Supabase keeps the exact SQL of every applied migration in `supabase_migrations.schema_migrations.statements`. The eight files above were read from there (read-only `select`) and written out unchanged. They are the real historical SQL, not a reconstruction. Integrity check: each file's size equals the stored length (plus one trailing newline where the original had none), for example `012` is 31,643 characters stored and 31,651 bytes in the file because of two multi-byte `••••` characters.

**Why `0030`, `0031` and `0040`.** Three of the live records never had a number. They first got letter names (`002a`, `002b`, `003a`), but the Supabase CLI only applies files named `digits_name.sql` and silently skips the rest, which would have dropped `signup_profile_fields` from any rebuild. Digits-only versions fix that: `0030` and `0031` sort after `002_hotfix` and before `003_remove_unrecorded_multivendor`, and `0040` sorts after `003_` and before `004_`. The new files are byte-for-byte copies of the old ones (identical git hashes). The `Migration files` check (`.github/workflows/migrations-check.yml`) fails a push if any file name would be skipped, if two files share a version, or if the first 19 do not replay in the live order.

**`003` removes what `0030` and `0031` create.** `003_remove_unrecorded_multivendor` drops the stores, orders and helper functions that `0030` built, because they had been added to the live database without files. Replaying all three reproduces live exactly.

**Note on `000` to `010`.** These files were already in the repo, but each is **larger** than the SQL stored live (for example `000` is 12,644 bytes in the repo against 11,616 characters stored). The likely cause is header comments added later, but this has not been confirmed line by line. They are not proven identical to what was applied. See `WEB-F07b`.

**What is still not proven.** Having the files is not the same as a working chain. The first real replay on an empty database is the staging run (`staging-db.yml`, see `ENVIRONMENTS.md`), together with the local replay in the CI `Database tests` job. Neither has reported on the 19-file chain yet. That is `WEB-F07b`. A replay must never be run against the live project. `docs/WORKFLOW/MIGRATION_RECOVERY.md` has the forensic evidence; `shared/sql/011_website_sync.sql` is an older partial copy and is superseded by `012`.

## How to add a database change
1. Read the table or function you are changing in the live database first.
2. Number it **034** or higher (029 is applied to staging; 030–033 are in the repository but not yet applied to staging). Digits, underscore, name, `.sql`.
3. Push it to `web-portal` for CI only. The `Database tests` job replays it locally. Staging application requires manual workflow dispatch with the explicit `APPLY` input (default `NO`) and owner approval; run the security advisors and compare the result with the intended schema/security contract.
4. Commit the reviewed migration and update this contract and the project tracker in the same PR.
